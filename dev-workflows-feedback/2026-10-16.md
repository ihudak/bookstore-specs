## 2026-10-16 — /scan — wrong-output

```yaml
id: NOKEY-scan-verify-scope-ignores-later-test
date: 2026-10-16
command: /scan
plugin_version: 0.1.0
origin: auto
author: ivan.gudak@dynatrace.com
category: wrong-output
impact: friction
```

**Friction:** `register.py verify-scope` (plugins/security-workflows/scripts/register.py, `verify_scope`) lists a `fixing` finding's file in `files` when its blob at the default ref differs from `last_seen.blob`. It runs rule 2's `_later` test only in the file-gone branch, not when the file is present. `plan` applies the later test to every finding, so the two disagree. In this run the default ref (`origin/master`) was the finding's `last_seen.base`, an ancestor of an unpushed `last_seen.commit`, and the fix was on an unpushed Epic branch too. `verify-scope` still scoped the file, so the run spent a Claude Security scan that could only be history for the finding and could close nothing. The orchestrator had to import register.py and call `_later`/`_changed` by hand to warn the user before the confirmation.

**Suggested improvement:** Run the rule-2 `_later` test in `verify_scope`'s file-present branch, and report the findings that fail it under a new key, such as `unreachable`. Keep a finding in `files` only where `_later` is True, and put it in `unverifiable` where it is None. In `/security-workflows:scan` Phase 1, stop with `SECURITY_NOTHING_TO_VERIFY` where `files` is empty and `unreachable` names findings, telling the user to push or merge the fix and re-run. Add a test for this shape: the default ref is an ancestor of `last_seen.commit`, and the fix is on a local branch only.

## 2026-10-16 — /scan — wrong-output

```yaml
id: NOKEY-scan-confirm-label-ignores-register-effect
date: 2026-10-16
command: /scan
plugin_version: 0.1.0
origin: auto
author: ivan.gudak@dynatrace.com
category: wrong-output
impact: polish
```

**Friction:** The Phase 3 confirmation of `/security-workflows:scan` always offers `"Start the scan (Recommended)"`, a fixed array presented verbatim. On a `--verify-fixes` run whose scan cannot close any scoped finding, the label recommends spending a significant number of tokens for no effect on the register. The orchestrator had to write a contrary recommendation into the question's prose.

**Suggested improvement:** Where the scope's findings cannot be closed by a scan at the default ref (the `unreachable` findings above), drop the "(Recommended)" marker from Start and name those findings in the confirmation question. Or recommend Cancel in that case.

## 2026-10-16 — /scan — wrong-output

```yaml
id: NOKEY-scan-verify-scope-ignores-later-test
date: 2026-10-16
command: /scan
plugin_version: 0.1.0
origin: auto
author: ivan.gudak@dynatrace.com
category: wrong-output
impact: friction
```

**Friction:** `register.py verify-scope` (plugins/security-workflows/scripts/register.py, `verify_scope`) lists a `fixing` finding's file in `files` when its blob at the default ref differs from `last_seen.blob`. It runs rule 2's `_later` test only in the file-gone branch, not when the file is present. `plan` applies the later test to every finding, so the two disagree. In this run the default ref (`origin/master`) was the finding's `last_seen.base`, an ancestor of an unpushed `last_seen.commit`, and the fix was on an unpushed Epic branch too. `verify-scope` still scoped the file, so the run spent a Claude Security scan that could only be history for the finding and could close nothing. The orchestrator had to import register.py and call `_later`/`_changed` by hand to warn the user before the confirmation.

**Suggested improvement:** Run the rule-2 `_later` test in `verify_scope`'s file-present branch, and report the findings that fail it under a new key, such as `unreachable`. Keep a finding in `files` only where `_later` is True, and put it in `unverifiable` where it is None. In `/security-workflows:scan` Phase 1, stop with `SECURITY_NOTHING_TO_VERIFY` where `files` is empty and `unreachable` names findings, telling the user to push or merge the fix and re-run. Add a test for this shape: the default ref is an ancestor of `last_seen.commit`, and the fix is on a local branch only.

## 2026-10-16 — /scan — wrong-output

```yaml
id: NOKEY-scan-confirm-label-ignores-register-effect
date: 2026-10-16
command: /scan
plugin_version: 0.1.0
origin: auto
author: ivan.gudak@dynatrace.com
category: wrong-output
impact: polish
```

**Friction:** The Phase 3 confirmation of `/security-workflows:scan` always offers `"Start the scan (Recommended)"`, a fixed array presented verbatim. On a `--verify-fixes` run whose scan cannot close any scoped finding, the label recommends spending a significant number of tokens for no effect on the register. The orchestrator had to write a contrary recommendation into the question's prose.

**Suggested improvement:** Where the scope's findings cannot be closed by a scan at the default ref (the `unreachable` findings above), drop the "(Recommended)" marker from Start and name those findings in the confirmation question. Or recommend Cancel in that case.

## 2026-10-16 — /scan — missing-capability

```yaml
id: NOKEY-scan-confirm-fp-evidence-verdict-not-surfaced
date: 2026-10-16
command: /scan
plugin_version: 0.1.0
origin: auto
author: ivan.gudak@dynatrace.com
category: missing-capability
impact: friction
```

**Friction:** In a `sec` `--triage` run, Phase 5 step 4 (plugins/security-workflows/commands/scan.md, unconfirmed rows) asks `Confirm` / `Overrule — fix it` / `Overrule — decide later` with no step that checks the dev's stored false-positive evidence against the source. `Confirm` then re-asserts that evidence verbatim (step 7). In this run the orchestrator checked it by hand before asking. The cited `file:line` was a truthiness check, not a guard. No code set the parameter the claim said only internal links set, and the ingress config held no rule matching the claimed stripping. The user confirmed anyway. The check was ad hoc, and the question itself carried no verdict.

**Suggested improvement:** Make the evidence check a fixed step before the unconfirmed-row question. The orchestrator reads the cited `path:line` at the finding's last-seen commit and states one line: holds, does not hold, or could not check, quoting the line it read. Where the evidence does not hold, the `Confirm` option says so (e.g. `Confirm (evidence does not hold)`). Optionally, `register.py ids`/`commit` could verify that the cited `path:line` exists at the finding's commit and print it, so the check is mechanical where it can be.

## 2026-10-16 — /scan — ambiguous-prompt

```yaml
id: NOKEY-scan-triage-batch-noop-for-unconfirmed-only
date: 2026-10-16
command: /scan
plugin_version: 0.1.0
origin: auto
author: ivan.gudak@dynatrace.com
category: ambiguous-prompt
impact: polish
```

**Friction:** Phase 5 step 2's batch question offers `Accept the suggestions` / `Change some` / `Decide all later`. When every row of the plan is review-due or unconfirmed, `Accept the suggestions` leaves each row as it stands, just as `Decide all later` does. The only way to act is `Change some`, so the user has to answer a second question every time. In this run the plan held only `unconfirmed: [2]`, and the orchestrator had to explain in the question that the first option does nothing.

**Suggested improvement:** Where every row is review-due or unconfirmed, skip the batch question and go straight to step 4's per-row question. Or drop `Accept the suggestions` from the array for such a plan.

## 2026-10-16 — /scan — missing-capability

```yaml
id: NOKEY-scan-fp-evidence-path-not-matched-to-finding
date: 2026-10-16
command: /scan
plugin_version: 0.1.0
origin: auto
author: ivan.gudak@dynatrace.com
category: missing-capability
impact: polish
```

**Friction:** Phase 5 step 5 asks again for false-positive evidence only where the answer holds no `<path>:<line>`. It does not compare the cited location with the finding's own `file:line`. In this run, evidence citing line 70 was recorded and later confirmed for a finding at line 71 of the same file. That was harmless there, but the same rule would accept a citation of an unrelated file.

**Suggested improvement:** In step 5, also ask again (or show the cited line for the user to accept) when the cited path differs from the finding's file, or when the cited line is more than a few lines from the finding's line with no reason given.
